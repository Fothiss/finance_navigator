# Spec Delta

## Purpose

Даёт финдиректору ответ «фиксировать кредит сейчас или подождать»: два независимых сигнала оценивают
вероятность повышения ключевой ставки ЦБ в ближайшие 30 дней по премии денежного рынка (RUSFAR1M)
и кривой ОФЗ к ключевой, сравнивают эти сигналы на истории и показывают бенчмарк надбавки по ставкам
МСП. Точечный прогноз не выдаётся — только вероятность с интервалом и измеренная точность.

## ADDED Requirements

### Requirement: Два независимых сигнала с общим таргетом

**Уровень нормативности:** MUST.

Система ДОЛЖНА считать два варианта сигнала — `rusfar_term_premium` и `ofz_curve_premium` — на одном
таргете «ключевая ставка через 30 дней выше, чем сегодня», на одном периоде истории и с одним baseline.
Таргет не зависит от варианта.

#### Scenario: Оба варианта присутствуют

- **WHEN** запрошен `GET /api/v1/money/signals`
- **THEN** ответ содержит массив `signals` ровно из двух элементов
- **AND** у каждого элемента есть `variant` из множества `rusfar_term_premium`, `ofz_curve_premium`
- **AND** у обоих одинаковые `target.event` и `target.horizon_days`

#### Scenario: Вердикт не зависит от другого варианта

- **WHEN** один вариант не прошёл бэктест, а второй прошёл
- **THEN** у первого `status` равен `insufficient_evidence` и `verdict` равен `null`
- **AND** у второго `status` равен `ok` и `verdict` непустой

### Requirement: Вероятность события отдаётся с интервалом

**Уровень нормативности:** MUST.

Каждый вариант ДОЛЖЕН отдавать вероятность события как число от 0 до 1 вместе с 80%-м доверительным
интервалом. Точечная вероятность без интервала недопустима.

#### Scenario: Интервал в каждом варианте

- **WHEN** вариант выдан со статусом `ok`
- **THEN** `probability.value` в диапазоне [0, 1]
- **AND** `probability.interval_80` содержит два числа, нижняя граница не больше `value`, верхняя не меньше
- **AND** `probability.n_observations` положительное

### Requirement: Рядом с оценкой всегда есть baseline

**Уровень нормативности:** MUST.

Каждый вариант ДОЛЖЕН содержать наивную оценку — безусловную частоту повышения ключевой за 30 дней
по всей истории — и величину прироста `lift = value - baseline.value`.

#### Scenario: Baseline присутствует

- **WHEN** вариант выдан со статусом `ok`
- **THEN** `probability.baseline.name` непустой
- **AND** `probability.baseline.value` в диапазоне [0, 1]
- **AND** `probability.lift` равен `value - baseline.value` с точностью до 0.001

### Requirement: Сигнал без пройденного бэктеста не выдаётся

**Уровень нормативности:** MUST.

Система ДОЛЖНА блокировать вердикт варианта, если его бэктест не пройден, не запускался или выборка
слишком мала. В этом случае `status` равен `insufficient_evidence`, а `verdict` и `probability` равны `null`.

#### Scenario: Бэктест не пройден

- **WHEN** `evidence.status` варианта равен `failed` или `not_run`
- **THEN** HTTP-статус ответа 200
- **AND** `status` варианта равен `insufficient_evidence`
- **AND** `verdict` и `probability` варианта равны `null`

#### Scenario: Слишком мало наблюдений

- **WHEN** `n_observations` варианта меньше настроенного минимума (по умолчанию 30)
- **THEN** `status` варианта равен `insufficient_evidence`
- **AND** в `evidence` варианта указана фактическая длина выборки

### Requirement: Вердикт вычисляется по настраиваемой политике

**Уровень нормативности:** MUST.

Пороги `p_borrow_now` и `p_wait` задают отображение вероятности в вердикт и ДОЛЖНЫ приниматься из
запроса: `p >= p_borrow_now` даёт `borrow_now`, `p < p_wait` даёт `wait`, иначе `watch`. Если клиент
пороги не передал, применяется значение по умолчанию из конфигурации. Политика одинакова для обоих
вариантов.

#### Scenario: Политика из запроса

- **WHEN** запрос содержит `p_borrow_now=0.70&p_wait=0.45`
- **THEN** `policy.source` равен `user`
- **AND** у каждого варианта `verdict` вычислен по этим порогам

#### Scenario: Политика по умолчанию

- **WHEN** запрос не содержит порогов и не содержит пресета
- **THEN** `policy.source` равен `default`
- **AND** использованы пороги из конфигурации

#### Scenario: Некорректные пороги

- **WHEN** запрос содержит `p_wait >= p_borrow_now`, отрицательное значение или значение больше 1
- **THEN** HTTP-статус 422
- **AND** тело ответа в формате `application/problem+json`

### Requirement: Пресеты политики доступны клиенту

**Уровень нормативности:** MUST.

Система ДОЛЖНА отдавать список именованных политик с порогами и признаком дефолтной, чтобы интерфейс
не дублировал числа в клиентском коде.

#### Scenario: Список пресетов

- **WHEN** запрошен `GET /api/v1/money/policies`
- **THEN** ответ содержит непустой список политик с полями `id`, `label`, `p_borrow_now`, `p_wait`, `is_default`
- **AND** ровно одна политика имеет `is_default` равный `true`
- **AND** для каждой политики `0 <= p_wait < p_borrow_now <= 1`

#### Scenario: Неизвестный пресет

- **WHEN** запрос сигналов содержит несуществующий `preset`
- **THEN** HTTP-статус 422
- **AND** тело ответа в формате `application/problem+json`

### Requirement: Параметры модели недоступны для изменения из интерфейса

**Уровень нормативности:** MUST.

Порог z-score, окно расчёта и минимум наблюдений ДОЛЖНЫ задаваться только конфигурацией. Запрос с
попыткой переопределить их ДОЛЖЕН быть отклонён.

#### Scenario: Попытка переопределить параметр модели

- **WHEN** запрос сигналов содержит `z_threshold`, `z_window` или `min_observations`
- **THEN** HTTP-статус 422
- **AND** в ответе указан неизвестный параметр

### Requirement: Варианты сравниваются на общем периоде

**Уровень нормативности:** MUST.

Система ДОЛЖНА сравнивать варианты по одной метрике на общем периоде и сообщать, является ли разница
устойчивой, а не объявлять лидера при шумовом преимуществе.

#### Scenario: Сравнение присутствует

- **WHEN** оба варианта имеют пройденный бэктест
- **THEN** ответ содержит `comparison` с полями `leader`, `metric` и `verdict`
- **AND** `comparison.verdict` равен `stable` или `inconclusive`

#### Scenario: Сравнение вычислимо

- **WHEN** `metric` равен `brier`
- **THEN** `leader` — вариант с меньшим значением метрики
- **AND** `by_variant` содержит значение метрики и `n` для каждого варианта

### Requirement: Бенчмарк надбавки по ставкам МСП

**Уровень нормативности:** MUST.

Система ДОЛЖНА отдавать разницу между ставкой по кредитам МСП и ключевой ставкой (надбавку рынка)
для ближайшего доступного месяца, не выдавая её за прогноз.

#### Scenario: Надбавка в сигнале

- **WHEN** запрошен `GET /api/v1/money/signals` и данные МСП доступны
- **THEN** ответ содержит `benchmark` с полями `sme_rate`, `key_rate`, `premium_bp` и `as_of`
- **AND** `premium_bp` равен разнице ставок в базисных пунктах

#### Scenario: Надбавка в серии

- **WHEN** запрошен `GET /api/v1/money/series`
- **THEN** ответ содержит месячный массив `rates` с `month`, `key_rate_avg` и `sme_rate`
- **AND** месячный массив не зависит от параметра бакета

### Requirement: Серии отдаются одним ответом

**Уровень нормативности:** MUST.

Система ДОЛЖНА возвращать в одном ответе обе премии (дневные, с бакетированием) и помесячные ставки
для бенчмарка.

#### Scenario: Ответ содержит все группы

- **WHEN** запрошен `GET /api/v1/money/series?from=2024-01-01&to=2026-02-13&bucket=week`
- **THEN** ответ содержит массивы `spreads` и `rates`
- **AND** `spreads` содержит ряды обоих вариантов с `date` и значением премии в базисных пунктах
- **AND** элементы `rates` имеют `month` в формате `YYYY-MM`

#### Scenario: Бакетирование меняет только дневные группы

- **WHEN** запрос выполнен с `bucket=day`, затем с `bucket=month`
- **THEN** количество элементов в `spreads` уменьшается при укрупнении бакета
- **AND** набор `rates` в обоих ответах одинаков при совпадающем диапазоне

#### Scenario: Некорректный диапазон дат

- **WHEN** `from` больше `to`, или `to` в будущем, или диапазон длиннее 10 лет
- **THEN** HTTP-статус 422
- **AND** тело ответа в формате `application/problem+json`

### Requirement: Устаревшие данные не превращаются в ошибку

**Уровень нормативности:** MUST.

Система ДОЛЖНА сообщать свежесть каждого источника. Если источник отстал больше чем на настроенный
допуск, ответ остаётся успешным, но помечается как устаревший.

#### Scenario: Данные устарели

- **WHEN** последняя дата источника старше настроенного допуска в днях
- **THEN** HTTP-статус 200
- **AND** `data.stale` равен `true`
- **AND** `status` равен `stale_data`
- **AND** `verdict` каждого варианта равен `null`

#### Scenario: Данные свежие

- **WHEN** все источники в пределах допуска
- **THEN** `data.stale` равен `false`
- **AND** `data.sources` содержит непустой `last_date` для каждого источника

### Requirement: Данные внешних систем кешируются

**Уровень нормативности:** MUST.

Система ДОЛЖНА получать данные ЦБ и MOEX через слой кеша и не обращаться к внешним API на каждый
запрос пользователя.

#### Scenario: Повторный запрос не идёт наружу

- **WHEN** два запроса сигналов выполнены подряд в пределах TTL
- **THEN** к внешним API ушло ровно по одному набору запросов на источник
- **AND** оба ответа содержат одинаковый `as_of`

#### Scenario: Источник недоступен

- **WHEN** внешний API вернул ошибку или не ответил за таймаут
- **THEN** HTTP-статус 503
- **AND** тело ответа в формате `application/problem+json`
- **AND** ранее закешированные данные не удаляются

### Requirement: Сигнал объясняется бизнес-языком

**Уровень нормативности:** MUST.

Каждый вариант ДОЛЖЕН содержать короткий вывод на русском языке и список факторов, определивших оценку.
Числа без объяснения недопустимы.

#### Scenario: Текст и факторы присутствуют

- **WHEN** вариант выдан со статусом `ok`
- **THEN** `headline` — непустая строка
- **AND** `drivers` содержит минимум один элемент с полями `code` и `impact`
- **AND** `indicators` содержит использованные значения с датой каждого

### Requirement: Контракты описаны в документации

**Уровень нормативности:** MUST.

Все публичные эндпоинты ДОЛЖНЫ быть описаны в `docs/API.md`: назначение, параметры, коды ответов и
примеры. Документ ДОЛЖЕН совпадать с OpenAPI-схемой приложения.

#### Scenario: Документ покрывает эндпоинты

- **WHEN** приложение запущено и OpenAPI-схема доступна
- **THEN** для каждой операции схемы в `docs/API.md` есть раздел с её методом и путём
- **AND** в документе описаны коды 200, 422 и 503
