# Design

## Context

Проект пустой: только `README.md`, `AGENTS.md` и каркас `openspec/`. Кода нет, слои создаются с нуля.
Мотив — `proposal.md`; требования — `specs/money-spread/spec.md`.

Результат спайка (12.11.2026), который определяет выбор источников:

- `KeyRateXML` (ЦБ SOAP): ключевая, ежедневно, с 2013-09-13.
- `RuoniaXML` (ЦБ SOAP): RUONIA, ежедневно, с 2010-01-11.
- ROISfix и MOSPRIME не рассчитываются с 01.03.2022 — терминальной структуры МБК у ЦБ нет.
- `hd_base/zcyc_params/` (ЦБ HTML): кривая бескупонной доходности ОФЗ, ежедневно, теноры 0.25…7 лет.
- MOEX ISS `history/.../RUSFAR1M.json`: премия денежного рынка на 1 месяц, ежедневно, с 2019-04.
- Ставка МСП — xlsx-бюллетень ЦБ («Таблица 5»), помесячно, машинно с 01.2024.

## Goals / Non-Goals

**Goals:**

- Два независимых сигнала о вероятности повышения ключевой за 30 дней, сравнимых между собой.
- Бенчмарк надбавки по ставке МСП — арифметика, а не прогноз.
- Вертикальный срез: внешние данные → индикатор → вероятность → бэктест → вердикт → экран.
- Контракты, которые не придётся менять при переходе на ML (меняются значения полей, не форма).

**Non-Goals:**

- ML-слой и `app/ml/`.
- Персистентность, аутентификация, история сигналов, фоновые задачи.
- Ввод пользовательской ставки («моя надбавка») — отдельный change.
- Модули 2 и 3.

## Decisions

### D1. Таргет — повышение ключевой за 30 дней, а не ставка МСП

`target_up(t) = key_rate(t+30) > key_rate(t)` (любое повышение). Причина: ставка МСП машинно доступна
с 01.2024 (мало), а ключевая — ежедневно с 2013 (тысячи наблюдений). Ставка по кредиту = ключевая +
надбавка банка; надбавка меняется медленно, поэтому направление кредитной ставки на 1–2 месяца вперёд
определяет ключевая. Ставка МСП остаётся в модуле как бенчмарк (см. D6), не как цель.

Альтернатива: прогнозировать саму ставку МСП (отклонено — 34 наблюдения, проверяемость нулевая).

### D2. Два независимых варианта + сравнение, не композит

Каждый индикатор считается отдельно до собственной вероятности и вердикта; объединение в один
композитный z отклонено, потому что правило-частотник в 2D-режиме схлопывает выборку, а бизнесу нужен
ответ «какой индикатор исторически точнее». Ответ `comparison` считает лидера по общей метрике (brier)
на общем периоде и помечает разницу как `stable`/`inconclusive`.

### D3. Индикаторы — премия за срок к ключевой, z-score по 250 дням

`rusfar_term_premium_bp = (RUSFAR1M - key_rate) * 100`;
`ofz_curve_premium_bp = (ОФЗ_1Y - key_rate) * 100`.

Метрика — z-score по скользящему окну 250 торговых дней: убирает зависимость от уровня ставок и
позволяет сравнивать эпохи. Режим — `z >= z_threshold` (по умолчанию 1.0). Абсолютный порог в базисных
пунктах отклонён: премия структурно меняет знак (рынок закладывает то ужесточение, то смягчение).

### D4. Оценка вероятности — правило (условная частота) на неперекрывающихся месяцах

`p = P(target_up | z >= z_threshold)` считается на месячной сетке (конец каждого месяца): это устраняет
перекрытие 30-дневных скользящих окон и даёт честное `n` (~150 месяцев с 2013). Интервал — Уилсон 80%.
Baseline — безусловная частота на той же сетке. ML заменяет только этот слой, не меняя схему ответа.

### D5. Политика — из query, дефолт в конфиге, модельные параметры закрыты

`resolve_policy` (query → пресет → дефолт) и `decide` (пороги → вердикт) — в `services/money/policy.py`.
Модельные параметры `z_threshold`, `z_window`, `min_observations` — только в settings; query-модели
объявлены с `extra="forbid"`, поэтому неизвестный параметр даёт 422, а не игнорируется.

### D6. Бенчмарк надбавки — арифметика на ставке МСП

`premium_bp = (sme_rate - key_rate) * 100` для последнего месяца бюллетеня; в `/series` — месячный ряд.
Не является прогнозом: это сравнение «сколько рынок берёт сверх ключевой». Парсер бюллетеня живёт в
`data/parsers/bulletin.py`, открывает только «Таблицу 5», история ограничена 01.2024 — допустимо, потому
что бенчмарк показывает текущий уровень, а не предсказание.

### D7. Источники — два клиента, один слой кеша

`clients/cbr_client.py` (SOAP `KeyRateXML` + HTML `zcyc_params` + xlsx-бюллетень) и
`clients/moex_client.py` (ISS JSON `RUSFAR1M`). Кеш — `cachetools.TTLCache` (TTL 1 день) + JSON-снапшот
`backend/.cache/` для офлайна и тестов. Redis не нужен при одном процессе.

### D8. Слои и защита от look-ahead

```
routers -> services -> {clients, data}
   |            |
   +--> schemas <+
config используется всеми слоями; models/ пуст
```

`services/money/` делится: `indicators` (премии, z-score), `target` (событие +30 дней, только прошлое),
`rule` (условная частота, Уилсон), `backtest` (метрики, статус, comparison), `policy` (пороги → вердикт),
`benchmark` (надбавка), `signal` и `series` (сборка ответов). Тест `test_money_no_lookahead` обрезает
датасет на случайной дате и проверяет неизменность прошлых строк.

### D9. Ошибки и свежесть

Ошибки — `application/problem+json` (RFC 7807): 422 для валидации и неизвестных параметров, 503 когда
данные недоступны вообще. Устаревшие данные — 200 + `status: "stale_data"` + `verdict: null`.

### D10. Схема ответа — источник типов

Pydantic-модели генерируют OpenAPI; TS-типы генерируются командой `npm run gen:api`. Инварианты
(verdict null при `evidence.status != passed`, обязательный `interval_80`) — в `model_validator` схемы.

### D11. Фронт — презентационные компоненты, запросы в хуках

Страница Money: `SignalCard` (по одной на вариант), `ComparisonPanel`, `PolicySelect`, `SpreadChart`
(обе премии), `BenchmarkPanel`, `StaleBanner`. Данные — `useMoneySignals` / `useMoneySeries`. Политика
в URL. Числа пресетов с `/policies`, в TS не дублируются.

### D12. Документация контрактов — часть DoD

`docs/API.md` описывает каждый эндпоинт; тест `test_api_doc_covers_openapi` сверяет операции OpenAPI
с разделами документа.

## Risks / Trade-offs

- **[Эффективность рынка]** премия может уже содержать всю информацию, `lift` окажется мал или
  отрицателен → это измеренный факт: `comparison` покажет `inconclusive` или вариант проиграет baseline,
  и `status` уйдёт в `insufficient_evidence`. Продукт не обещает lift, а измеряет его.
- **[Корреляция индикаторов]** RUSFAR и ОФЗ коррелированы → два варианта не дают независимой
  информации, выигрыш в устойчивости, а не в точности → `comparison` честно показывает разницу.
- **[Парсинг КБД]** HTML-таблица `zcyc_params` может менять вёрстку; история отдаётся постранично →
  парсер с тестами на фикстурах; спайк глубины истории отдельной задачей.
- **[Семантика RUSFAR]** `CLOSE` подтверждён как ставка в процентах (14.01 при ключевой 14.00), но
  требуется финальная проверка единиц и глубины → спайк в задачах.
- **[Ставка МСП короткая]** бенчмарк ограничен 01.2024 → допустимо для бенчмарка, помечено в `data`.
- **[Один процесс]** in-process кеш дублируется при нескольких воркерах → на MVP один воркер Uvicorn.
- **[Подгонка порогов]** пользователь может подобрать порог под желаемый вердикт → `policy.source`,
  `recommended_verdict` и бейдж «политика изменена» в UI.

## Migration Plan

Не применимо: первый деплой. Откат — удаление новых каталогов.

## Open Questions

- Заменить in-process кеш на Redis — при появлении второго инстанса.
- Ввод пользовательской ставки («моя надбавка») — отдельный change, бенчмарк к этому готов.
- Выбор ML-моделей и признаков — следующий change; схема ответа от этого не меняется.
- Добавление RUONIA как третьего индикатора — если потребуется ещё один независимый взгляд.
